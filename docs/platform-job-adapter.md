# 平台异步任务兼容与恢复

KY DNSPup 使用 DNSPup 客户 API。本文说明能力协商、进度、结果恢复及重复提交的边界，完整接口见 [客户 API 契约](reference/customer-api-v1.md)。

## 能力协商

唯一开启条件是已鉴权的 `GET /v1/account` 返回：

```json
{"data":{"capabilities":{"asyncProbesV1":true}}}
```

字段缺失、`false`、字符串等非布尔 `true` 值，都继续使用原同步上游 API。本地现有前台提交 `Prefer: respond-async`，只有协商通过后才使用平台异步模式；未声明异步的本地 API 调用仍维持原同步响应契约。

是否使用异步模式始终以当前账户的能力协商结果为准，不根据站点版本、健康接口或节点字段推断。站长无需配置平台内部开关。

## 创建与查询

创建请求为 `POST /v1/probes`，同时发送：

```http
Prefer: respond-async
Idempotency-Key: <本站的 X-Request-ID>
```

请求正文仍为六类工具原有参数。接受响应为 `data: { requestId, status, completedNodes, totalNodes, result? }`，其中上游请求编号为 `req_` 加 24 位十六进制字符。完整 `result` 使用原同步检测结果正文。

取得有效上游 ID 后，本站先保存 ID，再通过 `GET /v1/probes/{requestId}` 查询。域名绑定的每一次查询都使用真实 GET 路径、空正文、新时间戳和 nonce 重新签名。查询不发送幂等键、不提交检测、不增加本站每日提交数；平台契约中查询也不扣检测额度。

浏览器查询与本站后台查询按任务合并。正常轮询至少间隔 2 秒，随运行中任务数放慢，为每 Key 180 次/分钟的查询桶留出余量，并尊重最长 60 秒的数字 `Retry-After`。任务超时进入 unknown 后的恢复查询也遵守等待时间，重启不清除该限制。后台只有一个定时器，每次网络查询最长等待 20 秒。

## 持久化与重启

本站 `calls.upstream_job` 只保存上游任务 ID、当前凭据的 SHA-256 指纹、平台状态、实际节点计数及下次查询时间，不保存 API Key、Secret、认证头、原始目标或完整结果正文。原有调用记录仍保存去除 URL 查询和片段后的目标，期限为 7 天。

- 运行中的平台任务在本站重启后从保存的 ID 继续 GET 查询；不会重新 POST。
- 完整检测结果仍只在本站内存中保存最多 20 份、10 分钟。缓存淘汰或本站重启后，可用保存的 ID 重新从平台取回结果，平台完整结果保留 24 小时。
- 平台保留幂等标记至少 30 天；这不表示本站保存 30 天的完整结果或调用记录。
- 平台返回 `410 result_expired` 后，本地标记过期，不再查询或重发该任务。
- 本站正常停服会中止本地查询并等待本地任务收尾，不取消平台检测。重启后仍可凭已保存 ID 恢复。
- 旧同步调用没有可查询的上游任务 ID。若本站在执行期间重启，仍标记为「结果未知」，不会伪造恢复成功或自动重新检测。

## 不重复执行的边界

同一本地请求 ID 仍校验访问来源和请求正文摘要；重放只能查询原任务或读取原结果，不再次扣本站提交数，不再次 POST。访问来源变化或其他来源查询统一拒绝，不能仅凭管理员已登录绕过访客绑定。

异步创建响应丢失、没有取得有效上游 ID 时，本站记为 `unknown`。由于没有可查询 ID，本地不会猜测 ID、降级为同步调用或自动再次提交。原请求可由平台已有幂等和调用证据排查。这一状态不等于平台未执行或未扣费。

已取得 ID 后，遇到 401、403、404、410、503、能力关闭或网络异常，都不会改为 POST。短暂查询错误可以继续 GET；超过本地等待期限时标记 `unknown` 并释放本站并发，后续仍可用原 ID 查询。Ping/TCPing/HTTP/DNS/Traceroute 沿用 90 秒本地等待期限，MTR 为 240 秒。

更换或清除客户凭据后，本站不会用新凭据查询旧凭据的任务，也不会把旧任务结果记为新凭据的首次接入成功。原访客在内存保留期内已取得的结果仍可查看。

## 状态与计费

本站并发按持久调用记录中的运行任务计算，平台已接受但尚未结束的任务也占用名额，浏览器关闭不会立即释放名额。后台查询确认终态或本地等待超时后释放。

平台状态 `queued/running` 在现有前台等待流程中保持运行状态；真实 `completedNodes/totalNodes` 随本地任务查询返回，直接更新原有 Ping/TCPing/HTTP 进度条与节点计数，不按时间估算完成比例。DNS/Traceroute/MTR 页面不提供同样的进度条。`unknown/failed` 任务若保留部分结果，则原样返回其顶层状态、路由 `partial/complete/sequence/hops/raw` 及六类工具原有结果结构，不改成成功。

本地每日提交数仍用于保守访问保护；平台是否接受、实际扣费、幂等有效期和账户用量，以平台记录为准。幂等保护覆盖重复受理和重复计量，不等同于节点实际执行的严格一次保证；执行证据不足时，平台可以返回 `unknown`。

## 验证与排障

自动化测试使用隔离数据目录和测试上游，执行 `npm test` 不需要真实客户凭据。测试覆盖能力协商、签名、恢复、同步兼容、未知结果、凭据隔离、并发和六类结果结构。

自行验收时，可选一个已授权节点发起一次检测，在运行中刷新同一页面确认继续查询；完成后再次找回原结果，并对比平台用量。用量比较应排除其他访客或同一 API Key 的并发调用。不要通过不断新建检测验证恢复，每个新请求都可能计量。

出现异常时，保存操作时间和请求编号，从管理端导出脱敏诊断，按 [任务查询与诊断](task-diagnostics.md) 排查。不要公开原始响应、客户凭据或完整数据库。
